[RLEF: GROUNDING CODE LLMS IN EXECUTION FEEDBACK WITH REINFORCEMENT LEARNING](https://arxiv.org/abs/2410.02089)

Jonas Gehring, Kunhao Zheng, Jade Copet, Vegard Mella, Quentin Carbonneaux, Taco Cohen, Gabriel Synnaeve

> Large language models (LLMs) deployed as agents solve user-specified tasks over multiple steps while keeping the required manual engagement to a minimum. Crucially, such LLMs need to ground their generations in any feedback obtained to reliably achieve the desired outcomes. We propose an end-to-end reinforcement learning method for teaching models to leverage execution feedback in the realm of code synthesis, where state-of-the-art LLMs struggle to improve code iteratively compared to independent sampling. We benchmark on competitive programming tasks, where we achieve new state-of-the art results with both small (8B parameters) and large (70B) models while reducing the amount of samples required by an order of magnitude. Our analysis of inference-time behavior demonstrates that our method produces LLMs that effectively leverage automatic feedback over multiple steps.

## Follow-Up Questions

1. RLEF trains models to leverage execution feedback iteratively, whereas standard LLMs treat each code generation attempt independently. What specific failure modes of independent sampling does the iterative feedback loop address, and why can't chain-of-thought prompting alone solve these?

2. The paper trains on competitive programming tasks where execution feedback (pass/fail on test cases) is the reward signal. How might this training objective differ from real-world software engineering feedback, and what capabilities might be learned or not learned as a result?

3. What does it mean for a model to "ground its generations in feedback" — specifically, what must change in the model's internal representations or generation behavior compared to a model that ignores prior execution results?

4. The method achieves state-of-the-art results while "reducing samples required by an order of magnitude." What is the relationship between sample efficiency and the quality of feedback grounding, and how does RL training alter the inference-time sampling strategy?

5. Both 8B and 70B models show improvements from RLEF. Does the benefit scale proportionally with model size, and what does this imply about whether grounding in execution feedback is primarily a capability issue (needing more parameters) or a training objective issue?

6. The multi-conversation flow involves formatting execution feedback and querying for an update. How sensitive is the method to the quality of feedback formatting — would different feedback representations (e.g., error messages vs. stack traces vs. diff outputs) lead to significantly different learning outcomes?

7. What are the key limitations of using execution feedback as a sole reward signal — for instance, how does the method handle problems where code passes all provided test cases but is subtly incorrect, or where the test suite itself is incomplete?

## Answers

**1.** Independent sampling fails because each attempt is statistically independent of prior failures — the model cannot use information from "this approach didn't compile" or "test case 3 fails" to systematically narrow its hypothesis space. Chain-of-thought prompting can help the model reason about why a solution might be wrong in principle, but without actually executing the code, the model can only reason about what it believes should happen, which may be incorrect (hallucinated execution traces). The iterative feedback loop directly addresses this by providing ground truth signals from actual execution: the model receives information about which test cases fail and with what output, enabling it to localize errors and generate targeted corrections rather than essentially sampling uniformly from the space of plausible solutions again.

**2.** Competitive programming test suites are highly adversarial and complete by design — the reward signal (pass/fail on all test cases) is a reliable proxy for correctness. Real-world software engineering feedback is far noisier: it may be incomplete (only some tests are written), subjective (code review comments), or delayed (bugs surface only in production). The RLEF training objective likely teaches the model to maximize test-passing behavior specifically, which may not generalize to producing maintainable, readable, or efficient code — qualities not measured by execution feedback. The model may also learn to exploit weaknesses in test suites (e.g., producing edge-case-correct but algorithmically incorrect solutions), a behavior not penalized in the competitive programming setting.

**3.** Grounding generations in feedback requires that the model's continuation distribution be conditioned on the specific execution result just received, rather than on the initial problem statement alone. At the representation level, this means attention patterns in the model must route information from the feedback tokens into the generation of the correction, updating the implicit "state" of what has been tried and failed. Behaviorally, it requires the model to produce qualitatively different outputs after seeing "test 3 fails: expected 5, got 7" versus "test 3 fails: runtime error" — demonstrating that the feedback content, not just its presence, is influencing generation. A model that ignores prior results effectively treats the multi-turn conversation as a fresh prompt each time, producing independent samples rather than iterative refinements.

**4.** Sample efficiency improves because RL training causes the model to concentrate probability mass on strategies that productively use feedback rather than sampling from the full (mostly unproductive) generation distribution. A well-grounded model quickly converges to a corrected solution through targeted edits rather than requiring many independent full solutions to eventually generate a correct one by chance. The RL training essentially optimizes the model's inference-time "search process" — the policy learns to allocate more generation budget to promising corrections rather than exploring solutions that ignore available information. This mirrors how an efficient human programmer quickly zeros in on the bug given a failing test case, whereas a brute-force approach would require trying many unrelated solutions.

**5.** The fact that both 8B and 70B models benefit from RLEF suggests the limitation being addressed is primarily a training objective issue rather than a fundamental capability gap. If it were purely a capability issue, smaller models would lack the representations needed to utilize execution feedback regardless of training. The proportional benefit likely differs: larger models may need less additional RL training to achieve good feedback grounding because they already have stronger code reasoning capabilities, while smaller models may benefit more in relative terms because their pre-RLEF behavior was more heavily biased toward ignoring feedback. This implies RLEF is broadly applicable across model scales and is correcting a systematic mismatch between standard pre-training/SFT objectives (which do not reward iterative correction) and the desired inference-time behavior.

**6.** The method is likely sensitive to feedback format quality, though the paper's design of structured feedback formatting (executing, verifying, and structuring the result) is designed to mitigate this. Different feedback representations could produce significantly different learning outcomes: error messages that identify the failing test case and the expected vs. actual output provide actionable localization information, while raw stack traces require more reasoning to interpret. The model's ability to parse and utilize feedback is limited by the distribution of feedback formats seen during RL training — if deployment feedback formats differ substantially, the grounding behavior may not transfer. Diff outputs (showing exactly what changed) might be useful for eliciting targeted corrections but could also confuse the model if it was trained on pass/fail-type feedback.

**7.** Using execution feedback as the sole reward signal has several key limitations. First, it is susceptible to "reward hacking" on incomplete test suites — code that passes all provided tests may be logically incorrect in general (e.g., it hardcodes the expected outputs for the provided test cases). Second, it provides no signal about code quality dimensions that execution cannot measure: readability, maintainability, computational complexity, or adherence to style guidelines. Third, for problems with stochastic or complex-to-specify correctness criteria (e.g., generating code that produces reasonable natural language), binary pass/fail signals are inadequate. The paper acknowledges this implicitly by focusing on competitive programming where test suites are typically exhaustive and the correctness criterion is well-defined, but this limits the direct applicability to broader software engineering tasks.
