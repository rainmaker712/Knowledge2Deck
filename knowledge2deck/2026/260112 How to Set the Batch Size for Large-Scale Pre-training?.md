[How to Set the Batch Size for Large-Scale Pre-training?](https://arxiv.org/abs/2601.05034)

Authors: Yunhua Zhou, Junhao Huang, Shuhao Xing, Yechen Zhang, Runyu Peng, Qiping Guo, Xipeng Qiu

> The concept of Critical Batch Size, as pioneered by OpenAI, has long served as a foundational principle for large-scale pre-training. However, with the paradigm shift towards the Warmup-Stable-Decay (WSD) learning rate scheduler, we observe that the original theoretical framework and its underlying mechanisms fail to align with new pre-training dynamics. To bridge this gap between theory and practice, this paper derives a revised E(S) relationship tailored for WSD scheduler, characterizing the trade-off between training data consumption E and steps S during pre-training. Our theoretical analysis reveals two fundamental properties of WSD-based pre-training: 1) B_min, the minimum batch size threshold required to achieve a target loss, and 2) B_opt, the optimal batch size that maximizes data efficiency by minimizing total tokens. Building upon these properties, we propose a dynamic Batch Size Scheduler. Extensive experiments demonstrate that our revised formula precisely captures the dynamics of large-scale pre-training, and the resulting scheduling strategy significantly enhances both training efficiency and final model quality.

## Follow-Up Questions

1. What is the Critical Batch Size concept originally proposed by OpenAI, and why does it fail to apply when using a Warmup-Stable-Decay (WSD) learning rate scheduler instead of a cosine or constant schedule?

2. The paper defines B_min (minimum batch size to reach a target loss) and B_opt (batch size that maximizes data efficiency). Why do these two quantities differ, and in what practical scenarios would you prioritize one over the other?

3. The E(S) relationship characterizes the trade-off between data consumption E and training steps S. How does increasing batch size affect this trade-off, and what does it mean geometrically to "move along" the E(S) curve?

4. How does the WSD scheduler's three-phase structure (warmup, stable, decay) interact with batch size dynamics differently than a standard cosine decay schedule? Why does the decay phase specifically complicate the original Critical Batch Size theory?

5. The proposed dynamic Batch Size Scheduler changes batch size during training. What are the practical engineering challenges of changing batch size mid-training in distributed systems, and how might this interact with gradient accumulation and memory constraints?

6. The paper claims improvements in both training efficiency and final model quality. Are these improvements inherently linked, or could a schedule exist that improves efficiency at the cost of quality — and how would you detect that trade-off?

7. How does this work relate to the broader question of compute-optimal training (Chinchilla scaling laws), and does having an optimal batch size schedule change the recommended token-to-parameter ratio for a given compute budget?

## Answers

**1.** The Critical Batch Size (CBS) concept from OpenAI (McCandlish et al., 2018) defines the batch size below which adding more data per gradient step provides diminishing returns — it is the point where gradient noise and gradient signal are in balance. Under cosine or constant learning rate schedules, the CBS is approximately constant throughout training, making it a useful fixed target. Under WSD, however, the learning rate drops sharply in the decay phase, which fundamentally changes the gradient noise-to-signal ratio: the large learning rate in the stable phase means the model is performing large update steps that benefit from noisier (smaller batch) estimates, while the decay phase benefits from larger batches to ensure stable convergence to the loss minimum. The CBS framework assumed a single stable learning rate context, so it cannot capture this phase-dependent behavior.

**2.** B_min is the smallest batch size that can still reach a target loss within a fixed training token budget — going below B_min means you're making too many small, noisy gradient steps to converge to the target quality. B_opt is the batch size that reaches the target loss while consuming the fewest total tokens, accounting for the compute cost of each step. They differ because larger batches are more data-efficient per step (more signal per gradient update) but also consume more tokens per step. In practice, you would prioritize B_min when you have a fixed compute budget and want to minimize wall-clock time (by using the minimum viable batch that still converges), and B_opt when you have a fixed data budget and want to maximize the quality achievable from that data (by using the most data-efficient batch size).

**3.** The E(S) relationship traces out a Pareto frontier: for a fixed target loss, you can achieve it with many small steps (low S, high E per step) or fewer large steps (high S, lower E per step via larger batches). Moving along the curve by increasing batch size shifts from one extreme to the other — you trade data consumption (total tokens) for step count (and hence wall-clock time with fixed hardware). Geometrically, each point on the curve represents a different (batch_size, total_tokens) combination that achieves the same target loss. The paper's contribution is deriving this curve specifically for WSD dynamics, where the shape changes compared to constant-LR training because the decay phase concentrates convergence work in a narrow step window, reshaping the efficiency frontier.

**4.** The WSD scheduler's stable phase involves a large, nearly constant learning rate for the majority of training, followed by an aggressive decay. During the stable phase, the model is exploring the loss landscape broadly, and the CBS is relatively low — small batches with noisy gradient estimates are sufficient because the learning rate dominates convergence. During the decay phase, convergence requires precise gradient estimates to follow the loss landscape to a sharp minimum; using too-small batches here introduces gradient noise that wastes the decay phase's potential. Standard cosine schedules continuously reduce the learning rate, so the CBS changes smoothly and predictably; WSD creates a discontinuous change at the decay onset that the original CBS theory's continuous-LR derivation cannot model.

**5.** Changing batch size mid-training in distributed systems is non-trivial for several reasons. First, gradient accumulation must be adjusted to maintain the target batch size — if the batch per device stays fixed but the number of accumulation steps changes, this is manageable, but changing the per-device batch size may require reallocating activations and KV cache, which can cause out-of-memory errors. Second, in data-parallel training, the effective learning rate is typically scaled with batch size (linear scaling rule); a dynamic batch schedule must therefore also adjust the learning rate accordingly, requiring the two schedules to be coordinated. Third, many distributed training frameworks assume a fixed global batch size for gradient synchronization, and changing it mid-run can require checkpointing and restarting workers. The paper presumably handles these through either accumulation-based batch changes (less disruptive) or by carefully coordinating with the LR scheduler.

**6.** Efficiency and quality improvements are not always inherently linked. In principle, a schedule could exist where training steps are reduced (higher efficiency) but the model converges to a worse local minimum (lower quality) — this would happen if large batches in the decay phase over-smooth the gradient signal and miss the sharpest quality minimum. The paper claims both improve together under the optimal schedule, which is plausible if the previous fixed-batch-size baselines were already operating in a regime where the batch size was misaligned with the LR phase. To detect the efficiency-quality trade-off empirically, you would compare: (a) token efficiency curves (loss vs. tokens consumed) across schedules, and (b) final loss at multiple batch sizes for the same total token budget — if the optimal batch schedule achieves lower loss at every token count, it is genuinely Pareto-dominating rather than just trading one for the other.

**7.** Chinchilla scaling laws derive compute-optimal token-to-parameter ratios assuming a fixed training setup, but they implicitly assume a roughly constant batch size throughout training and do not optimize for batch schedule. If the dynamic batch schedule significantly improves data efficiency (fewer tokens needed to reach a given loss), it effectively shifts the Chinchilla frontier: the model reaches target quality with fewer tokens, meaning you could either train on fewer tokens (saving cost) or use the saved token budget to train a larger model. However, the Chinchilla ratio itself (approximately 20 tokens per parameter for compute optimality) is derived from the total compute budget, not just tokens — changing the batch schedule doesn't change the FLOPs per token, so the ratio's compute-based derivation remains valid. What changes is that the effective token count needed to hit a quality target decreases, which would allow slightly larger models for the same total compute by saving on the data consumption side.
